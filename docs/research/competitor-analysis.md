# Seven platforms share one automation engine

All seven platforms run the same basic machine: a stored workflow definition, a way to detect events, a saved record of each run, a worker that executes one step at a time using mapped data and stored credentials, and a history that lets someone inspect and retry what happened. They differ mainly in four decisions: the shape of the workflow graph, the unit of data that moves between steps, how and when run state is saved, and what the customer is charged for. The common core is smaller than the feature lists suggest: triggers, branching, data mapping, encrypted connections, a generic HTTP step, step-level run history, and retry or replay. Approvals, environments, audit, custom roles, templates and AI builders are layers on top, and most vendors sell the governance ones on higher plans. For FlowBridge, this means the first thing to build is a durable run engine with real step records and pinned workflow versions, followed by trigger handling and encrypted connections, and only then the polished canvas. Several vendors are visibly retrofitting exactly this durability: n8n added a database-backed scheduler, Zapier launched a separate durable engine in September 2026, and Pipedream is closing Workflows altogether on 31 March 2027 to focus on its integration layer. No page used in this research required a login, and no login was attempted, so the unverified items at the end confirm details rather than block design. FlowBridge's internship length, team size and target users were not in the notes, so the build order below is sequenced by dependency rather than by calendar.

## Four design choices separate products that otherwise match

The table summarises what each product is, as documented on 7 November 2026. Several are mid-transition, which matters when reading their docs: n8n's stable line is 2.x while 3.x is rolling out ([n8n releases](https://github.com/n8n-io/n8n/releases)); Zapier's Classic Zaps coexist with Next Gen Zaps, TypeScript workflows in early access ([Zapier community announcement](https://community.zapier.com/product-updates/the-next-generation-of-zaps-is-here-53832)); Make scheduled the removal of cycles for 1 October 2026 and replaced operations with credits as the billing unit ([Make cycles removal](https://help.make.com/cycles-removal-on-october-1-2026), [Make credits](https://help.make.com/credits)); Workato's names are shifting across Tasks, Business actions and Credits ([Workato pricing FAQs](https://docs.workato.com/en/pricing/pricing-faqs.html)); and Pipedream Workflows no longer accepts signups ([Pipedream shutdown notice](https://pipedream.com/docs/workflows)).

| Platform | What you build | What moves between steps | What is metered | Engine publicly described |
|---|---|---|---|---|
| n8n | Graph of named nodes that can branch, merge and loop | Array of items; nodes run once per item | Whole workflow runs | Yes: Postgres, Redis (Bull), workers |
| Zapier Classic | One trigger plus ordered steps; branches never rejoin | Each step's output, mapped as pills | Successful action steps (tasks) | No |
| Make | Chain or tree of modules; only If-else can rejoin | Bundles, one at a time through the chain | Credits, normally 1 per module run | Run phases yes, workers no |
| Power Automate | JSON definition ordered by `runAfter` edges | Typed outputs, read through expressions | Licence plus daily requests, counting every trigger and action | Partly, through Logic Apps docs |
| Workato | Trigger plus a tree of steps; usually one job per event | Typed datapills | Tasks, Business actions or Credits, by contract | No |
| Pipedream | Steps and blocks compiled into function segments | JSON exports under `steps.name` | Compute time | Partly: per-version VMs on AWS |
| Activepieces | Trigger plus a tree of actions, stored as JSON | Step outputs referenced with `{{ }}` | One credit per run, more for AI | Yes, in unusual detail |

**Graph shape** decides what users can express and how hard the engine is to write. Zapier's Classic Paths must be the final step, so shared actions cannot follow them ([Zapier Paths](https://help.zapier.com/hc/en-us/articles/8496288555917-Add-branching-logic-to-Zap-workflows-with-Paths)). Make has no converger for routers, and its Merge module works only with If-else ([Make converger](https://help.make.com/converger), [Make If-else](https://help.make.com/if-else-and-merge)). Power Automate's underlying engine uses one compact mechanism, where each action names its predecessors and the statuses it accepts from them, and that gives ordering, joins and error paths at once ([Logic Apps error handling](https://learn.microsoft.com/en-us/azure/logic-apps/error-exception-handling)). Zapier's Next Gen announcement lists splitting and merging branches among its headline additions, which suggests the Classic limit was structural (my inference).

**The data unit** decides how many times a step runs. In n8n, two incoming items make a Trello node create two cards, so most loops are invisible, and when an output cannot be linked back to its source item n8n raises an error ([n8n item linking](https://docs.n8n.io/build/work-with-data/reference-data/link-data-items/how-items-link-through-workflows)). In Make, ten bundles passing through three modules plus a trigger costs 31 operations, and each bundle finishes the chain before the next begins ([Make operations](https://help.make.com/operations), [Make execution flow](https://help.make.com/scenario-execution-flow)). Power Automate, Workato and Activepieces use the plainer model: a step produces one output, and iteration is an explicit loop block.

**State saving** decides what survives a crash. Activepieces overwrites one compressed run log at start, every 15 seconds and at the end, then resumes by walking from the trigger and returning saved outputs for finished steps ([Activepieces durable execution](https://www.activepieces.com/docs/install/architecture/durable-execution)). n8n offers per-node saving as a setting with a latency cost ([n8n workflow settings](https://docs.n8n.io/build/manage-workflows/configure-workflow-settings)). Workato reruns from stored trigger data through the whole recipe ([Workato rerun](https://docs.workato.com/recipes/rerun-job.html)).

**The meter** shapes user behaviour, and is covered under limits and pricing below.

## One run, followed from event to history

This walk through follows a composite run. No single vendor documents this exact pipeline, so the sequence is my synthesis, with each mechanism attributed to the platform that documents it. The workflow: a customer submits an order through a webhook, FlowBridge looks the customer up in a CRM, an order above a threshold goes to a manager for approval, an invoice is created in an accounting system, and a Slack message goes out.

**Before any event: publishing prepares the trigger.** Publishing freezes a version and tells the outside world where to send events. For a webhook trigger, the platform calls the source system's subscribe API with a callback URL, and keeps the address it needs to delete that subscription later. Microsoft requires the service to return a `Location` header for that delete ([Microsoft webhook trigger](https://learn.microsoft.com/en-us/connectors/custom-connectors/create-webhook-trigger)). Workato's connector kit adds a refresh hook for subscriptions that expire ([Workato SDK triggers](https://docs.workato.com/developing-connectors/sdk/sdk-reference/triggers.html)). n8n re-registers only the triggers that changed and reports "Published, partial" when some fail ([n8n publish](https://docs.n8n.io/build/understand-workflows/save-and-publish-workflows)). Activepieces fails the publish if the enable hook fails ([Activepieces triggers](https://www.activepieces.com/docs/build-pieces/piece-reference/triggers/overview)).

**Step 1: the event arrives and is accepted.** An HTTP request reaches a public URL. The platform checks size and rate, then replies quickly so the sender does not time out. Limits vary widely: 512 KB on Pipedream without its upload option, 5 MB on Activepieces Cloud, 10 MB on Zapier, 16 MB on n8n and 50 MB on Workato ([Pipedream limits](https://pipedream.com/docs/workflows/limits), [Activepieces limits](https://www.activepieces.com/docs/install/reference/limits), [Zapier webhooks](https://help.zapier.com/hc/en-us/articles/8496288690317-Trigger-Zaps-from-webhooks), [n8n webhook](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/), [Workato quotas](https://docs.workato.com/en/recipes/limits.html)). The 200 reply is a promise, and it can be broken: Activepieces says that losing Redis data loses queued jobs, including webhooks already answered with 200 ([Activepieces disaster recovery](https://www.activepieces.com/docs/install/guarantees/disaster-recovery)).

**Step 2: duplicates and irrelevant events are dropped.** Senders retry, so the same event can arrive twice. Zapier applies no deduplication to instant triggers and assumes the sender only sends new data ([Zapier duplicates](https://help.zapier.com/hc/en-us/articles/8496260269965-How-Zapier-handles-duplicate-data-in-Zap-workflows)). Activepieces drops repeats that share a dedupe key for 30 seconds ([Activepieces dedupe service](https://github.com/activepieces/activepieces/blob/main/packages/server/api/src/app/trigger/dedupe-service.ts)). A filter may also run here. Power Automate's trigger conditions stop a run before it exists, which saves both quota and history clutter ([Microsoft trigger conditions](https://learn.microsoft.com/en-us/power-automate/customize-triggers)).

**Step 3: a run record is created and queued.** The platform writes a run row and places only its ID on a queue. n8n's flow is explicit: the main process creates the execution without running it, sends the ID to Redis, and a worker picks it up and loads the workflow from the database ([n8n queue mode](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode)). This keeps the queue small and makes the database the single source of truth (my inference). If the customer is at capacity, policy decides what happens next. Make queues asynchronous runs silently but answers callers waiting on a webhook response with a 429, because queuing would break the behaviour they designed ([Make parallel capacity](https://help.make.com/parallel-capacity)).

**Step 4: a worker claims the run on a lease.** A worker takes the job and holds a time-limited claim that it must keep renewing, so that if it dies the job can be noticed and recovered. n8n's defaults are a 60-second lease, a 10-second renewal and a 30-second stalled-job check ([n8n queue variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/queue-mode)). The worker loads the workflow version recorded for the run. n8n stores the workflow as it was at run time alongside the run data ([n8n database](https://docs.n8n.io/deploy/host-n8n/understand-the-architecture/understand-the-database)). Activepieces then allocates a sandbox and runs the engine in it over a WebSocket ([Activepieces architecture](https://www.activepieces.com/docs/install/architecture/overview)).

**Step 5: inputs for the CRM step are resolved.** The engine replaces each reference such as "email from the trigger" with this run's real value and coerces it to the field's type. Failures here are easy to miss. Zapier silently substitutes the run time for an unparseable date ([Zapier field types](https://help.zapier.com/hc/en-us/articles/8496259603341-Field-types-in-Zaps)), and Make coerces any number, even 0, to Yes for a Boolean field ([Make type coercion](https://help.make.com/type-coercion)). Activepieces produces two copies of the inputs, one resolved for use and one censored for logs ([Activepieces props resolver](https://github.com/activepieces/activepieces/blob/main/packages/server/engine/src/lib/variables/props-resolver.ts)).

**Step 6: the credential is fetched and, if needed, refreshed.** The workflow holds a reference, never the secret. The engine decrypts the connection for just this call. If the API answers that the token has expired, n8n's code re-reads the stored credential first: if the token has changed, another process already refreshed it, so that token is used. That avoids two workers fighting over a refresh without a distributed lock ([n8n oauth.ts](https://github.com/n8n-io/n8n/blob/master/packages/core/src/execution-engine/node-execution-context/utils/request-helpers/oauth.ts)). If the refresh token is dead, the run needs a person. Zapier puts such runs On hold and keeps their trigger data, so they replay cleanly after reconnecting ([Zapier held runs](https://help.zapier.com/hc/en-us/articles/37454233721869-How-to-troubleshoot-held-Zap-or-step-runs)).

**Step 7: the outbound call runs under a time budget.** Zapier gives create and search actions 30 seconds, and on timeout admits that the outcome is unknown, because the action may still have finished ([Zapier action timeouts](https://docs.zapier.com/platform/build/troubleshoot-action-timeouts)). Most Make modules get 40 or 60 seconds ([Make errors](https://help.make.com/fix-errors-and-warnings)), and Power Automate's synchronous calls get 120 seconds ([Microsoft limits](https://learn.microsoft.com/en-us/power-automate/limits-and-config)). Slow operations use a callback, so the step returns, shows as waiting, and resumes when the service posts back ([Zapier action timeouts](https://docs.zapier.com/platform/build/troubleshoot-action-timeouts)).

**Step 8: the output is saved and the next step is chosen.** The response becomes data for later steps and is written to the run's history, usually with a size limit. Workato keeps at most 1 MB of inputs and outputs across a job's details, Pipedream caps logs, exports and event data at 6 MB per execution, and Activepieces slices outputs above 32 KB in the run log ([Workato quotas](https://docs.workato.com/en/recipes/limits.html), [Pipedream limits](https://pipedream.com/docs/workflows/limits), [Activepieces limits](https://www.activepieces.com/docs/install/reference/limits)). The engine evaluates the amount condition and follows the approval branch. References to steps on an untaken branch are a known hazard: Workato's are typically blank, and n8n raises "Referenced node is unexecuted" ([Workato datapills](https://docs.workato.com/recipes/data-pills-and-mapping.html), [n8n expressions](https://docs.n8n.io/build/work-with-data/transform-data/expressions-for-data-transformation)).

**Step 9: the run pauses for approval and gives up its worker.** Nothing should sit in memory waiting for a manager. In Activepieces, the action runs twice: on BEGIN it creates a durable waitpoint row, and on RESUME it reads the payload. A unique constraint on run plus step absorbs duplicate callbacks, and if the callback beats the pause, a pre-completed row handles the race ([Activepieces waitpoints](https://www.activepieces.com/docs/install/architecture/waitpoints), [Activepieces flow control](https://www.activepieces.com/docs/build-pieces/piece-reference/flow-control)). n8n's Wait node saves execution data to the database, unless the wait is under 65 seconds, and creates a unique per-execution resume URL ([n8n Wait](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait)).

**Step 10: the manager responds and the run resumes.** Clicking the link reloads the saved state and re-queues the run, possibly on a different worker. The workflow may have been edited in the meantime. Workato keeps paused jobs on the version they began with ([Workato jobs](https://docs.workato.com/recipes/jobs.html)), and Zapier's Next Gen pins runs the same way ([Zapier Next Gen drafts](https://help.zapier.com/hc/en-us/articles/49007970890509-Create-Next-Gen-Zap-drafts-and-versions)). Classic Zaps can instead fail step replay with "Zap has diverged too much" after a structural change ([Zapier diverged](https://help.zapier.com/hc/en-us/articles/16813373170317-Zap-error-Zap-has-diverged-too-much)).

**Step 11: the accounting API fails, and the retry logic takes over.** The API returns 503. Temporary failures (408, 429, 5xx) get retried and permanent ones do not ([Logic Apps error handling](https://learn.microsoft.com/en-us/azure/logic-apps/error-exception-handling)). If retries run out, the step's error path runs if one exists; otherwise the run fails and its later steps are skipped. The dangerous case is a timeout on "create invoice", since a retry could create a second invoice. Only Power Automate and Activepieces state the guarantee plainly: delivery is at-least-once, so side effects can repeat ([Microsoft triggers troubleshooting](https://learn.microsoft.com/en-us/troubleshoot/power-platform/power-automate/flow-run-issues/triggers-troubleshoot), [Activepieces crash recovery](https://www.activepieces.com/docs/install/guarantees/crash-recovery)).

**Step 12: the run finishes and leaves its trail.** The Slack step succeeds and the run gets a final status. Usage is counted, an alert fires if the run failed, and later a retention job deletes the payloads. n8n's defaults prune runs older than 14 days or beyond 10,000, while exempting running and waiting runs ([n8n execution data](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/manage-execution-data)). If the worker had died at any point, the lease would have expired. n8n's recovery marks such runs as `crashed` ([n8n execution status](https://github.com/n8n-io/n8n/blob/master/packages/workflow/src/execution-status.ts)), and Activepieces re-runs them from the checkpoint ([Activepieces crash recovery](https://www.activepieces.com/docs/install/guarantees/crash-recovery)). The product feels simple because of these steps, and most of the engineering effort sits in steps 3, 4, 8, 9 and 11, which users never see (my judgement).

## How each functional area works and where the platforms split

### Triggers separate how an event is detected from how it becomes runs

There are three detection mechanisms. A **webhook** is a push: the source system calls a URL when something happens. **Polling** is a pull: the platform asks "anything new?" on a timer and remembers where it got to, in a saved position called a cursor. A **schedule** fires on the clock. n8n adds long-lived connections such as message queues and IMAP ([n8n node types](https://docs.n8n.io/connect/create-nodes/plan-your-node/choose-a-node-type)), and Workato lists change data capture as well ([Workato triggers](https://docs.workato.com/recipes/triggers.html)). Workato's useful contribution is a second axis: once an event is detected, it can become one job, a batch or a bulk stream ([Workato triggers](https://docs.workato.com/recipes/triggers.html)). A batch size of 100 and 420 events yields five jobs.

Polling hides most of the subtlety. Zapier compares each item's ID against a stored per-Zap list, reads only the first page, and takes a snapshot when a Zap is turned on, called priming, so existing records do not fire ([Zapier deduplication](https://docs.zapier.com/platform/build/deduplication)). Updated-record triggers combine ID and timestamp, so each update looks new. Workato's kit requires exactly this kind of signature, for example `id@updated_at` ([Workato SDK triggers](https://docs.workato.com/developing-connectors/sdk/sdk-reference/triggers.html)). Microsoft's connector contract is the cleanest for authors: the first call returns 202 with a location header holding the state, and each later call uses that location, so connector authors keep no database ([Microsoft polling trigger](https://learn.microsoft.com/en-us/connectors/custom-connectors/create-polling-trigger)). Pipedream's `unique` strategy keeps a FIFO cache of only 100 IDs ([Pipedream component API](https://pipedream.com/docs/components/contributing/api)).

The platforms disagree on what happens after downtime. Power Automate's polling triggers catch up on everything pending, and its only documented way to skip the backlog is to copy the flow and delete the original; webhook events during the off period are lost ([Microsoft optimize triggers](https://learn.microsoft.com/en-us/power-automate/guidance/coding-guidelines/optimize-power-automate-triggers)). Workato's polling also resumes where it stopped ([Workato start and stop](https://docs.workato.com/recipes/start-and-stop.html)), and most of its real-time triggers poll roughly hourly in the background to recover dropped events ([Workato triggers](https://docs.workato.com/recipes/triggers.html)). Zapier clears its dedupe list when a Zap is turned off, then re-primes on restart ([Zapier deduplication](https://docs.zapier.com/platform/build/deduplication)), which means polling events during downtime are lost (my inference from that behaviour). Users should choose this explicitly at turn-on.

Schedules looked easy until they were not. n8n's old in-memory timers lost runs across restarts, so from version 2.45.0 upcoming runs are database rows that instances claim, with a reaper for crashed claims and a grace period for late firing. By default it does not replay a missed run after that grace period ([n8n durable scheduler](https://docs.n8n.io/deploy/host-n8n/configure-n8n/durable-scheduler)). Polling intervals are a commercial lever at Zapier, running from 15 minutes on Free to 1 minute on Team ([Zapier triggers](https://help.zapier.com/hc/en-us/articles/8496244568589-How-Zap-triggers-work)), and at Power Automate, whose documented examples are 15 and 5 minutes ([Microsoft triggers troubleshooting](https://learn.microsoft.com/en-us/troubleshoot/power-platform/power-automate/flow-run-issues/triggers-troubleshoot)).

### Logic is mostly the same blocks with very different limits

Branch, loop, wait and call-another-workflow exist nearly everywhere. The differences are in the limits, and in whether branches can rejoin.

| Platform | Branching | Rejoin | Loops | Longest documented wait | Human approval |
|---|---|---|---|---|---|
| n8n | If, Switch, Filter | Merge waits for all inputs | Implicit per item, plus Loop Over Items | Not stated | Send-and-wait nodes, Slack, Wait with form |
| Zapier Classic | Filter, Paths (10 branches, 3 levels) | None | Looping beta: one per Zap, 500 iterations | 30 days | Human in the Loop, premium |
| Make | Router (all matching), If-else (first match) | Merge, with If-else only | Iterator or Repeater plus Aggregator | Sleep 300 seconds | None found; split scenarios for long pauses |
| Power Automate | Condition, Switch (25 cases) | `runAfter` joins (Logic Apps docs) | Apply to each, Do until | 30 days from run start | Approvals connector |
| Workato | IF, ELSE IF, ELSE | None documented | Repeat for each, Repeat while (50,000) | 732 days | Wait for user action |
| Pipedream | If/Else, Switch, Parallel, Filter | Block End phase | Code only | 1 year (Delay); suspend defaults to 24 hours | Resume URLs, no built-in UI |
| Activepieces | Router (first or all match), AI Router | Barriers wait for N signals | Sequential loop | 30 days | Approval piece, 2-of-3 and veto via barriers |

Some semantics surprise people. Microsoft's Do until runs at least once, and in Logic Apps docs only its final iteration decides the loop's status ([Logic Apps loops](https://learn.microsoft.com/en-us/azure/logic-apps/logic-apps-control-flow-loops)). Workato's Repeat while is also do-while, with its cap described as protection against uncontrolled task consumption ([Workato loops](https://docs.workato.com/en/recipes/loops)). Each Zapier loop iteration creates a separate run, and the page describes no way to combine the results ([Zapier Looping](https://help.zapier.com/hc/en-us/articles/42969233918477-Understanding-Looping-by-Zapier)). Workato's async function calls return no data, so its documented workaround is writing results to a lookup table ([Workato async call](https://docs.workato.com/en/connectors/recipe-functions/actions/call-recipe-function-asynchronously)). n8n's multi-branch order depends partly on canvas position, so moving a node can change behaviour ([n8n execution order](https://docs.n8n.io/build/flow-logic/understand-execution-order)).

Reuse through sub-workflows exists in all seven, with a recurring trap around lifetimes and failure. A Zapier parent stays Delayed indefinitely if its sub-Zap returns nothing ([Zapier Sub-Zap](https://help.zapier.com/hc/en-us/articles/32283713627533-Understanding-the-Sub-Zap-app)). n8n parks the parent at a waiting state until the child finishes ([n8n wait tracker](https://github.com/n8n-io/n8n/blob/master/packages/cli/src/wait-tracker.ts)). Power Automate cannot pass connections from parent to child ([Microsoft child flows](https://learn.microsoft.com/en-us/power-automate/create-child-flows)).

Custom code needs real isolation, and that is expensive. Zapier gives 1 second on Free up to 2 minutes on Enterprise ([Zapier Code](https://help.zapier.com/hc/en-us/articles/45405528551181-Using-Code-by-Zapier)). Make runs JavaScript or Python in a sandbox for 30 to 300 seconds ([Make Code](https://help.make.com/the-make-code-app-is-available)). Workato's Python gets 90 seconds and no user-provided libraries ([Workato Python](https://docs.workato.com/connectors/python.html)). n8n calls task runners "the only isolation layer", and says that without them a workflow editor could read the database and encryption key ([n8n task runners](https://docs.n8n.io/deploy/host-n8n/configure-n8n/set-up-task-runners)). Activepieces ships `UNSANDBOXED` as its default mode, and its stronger process sandbox needs a privileged container ([Activepieces env vars](https://www.activepieces.com/docs/install/reference/environment-variables), [Activepieces sandboxing](https://www.activepieces.com/docs/install/architecture/sandboxing)). The notes did not surface a general code step for Power Automate cloud flows.

### Data mapping is a friendly picker over one expression language

Every product shows a step's possible outputs and lets the builder drop them into later fields. The best-documented design treats the picker as only a UI: dragging a field in n8n writes `{{ $json.fruit }}` ([n8n data structure](https://docs.n8n.io/build/work-with-data/understand-n8ns-data-structure)), and Power Automate's dynamic content and hand-written expressions share Workflow Definition Language ([Microsoft expressions](https://learn.microsoft.com/en-us/power-automate/use-expressions-in-conditions)). The language itself is the riskier choice. n8n and Pipedream evaluate JavaScript inside braces, which is why n8n now has several expression engines, with the legacy one running without isolation ([n8n expression engine](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/expression-engine), [Pipedream props](https://pipedream.com/docs/workflows/building-workflows/using-props)). Workato uses a Ruby-derived language restricted to an allowlist ([Workato formula mode](https://docs.workato.com/formulas/formula-mode.html)). Make and Activepieces offer function catalogues with a type or preview aid ([Make functions](https://help.make.com/use-functions), [Activepieces formulas](https://www.activepieces.com/docs/flows/using-formulas)). Zapier's Classic product relies on Formatter and Code steps, and no page read documents an expression language.

The picker needs to know a step's output shape before it has run, and this is solved in four ways. Connectors declare it, as with Workato's `output_fields` ([Workato SDK triggers](https://docs.workato.com/developing-connectors/sdk/sdk-reference/triggers.html)). The platform learns it from a test call, as Make does with "Run this module only" ([Make Iterator](https://help.make.com/iterator)). Sample data supplies it, as in Zapier's test records and Activepieces' mandatory step tests ([Zapier mapping](https://help.zapier.com/hc/en-us/articles/8496343026701-Send-data-between-steps-by-mapping-fields), [Activepieces passing data](https://www.activepieces.com/docs/flows/passing-data)). Or a schema is snapshotted, which is why Power Automate cannot see a new SharePoint column until the action is deleted and re-added ([Microsoft designer](https://learn.microsoft.com/en-us/power-automate/flows-designer)). Workato instead creates a "Schema change" recipe version automatically ([Workato versions](https://docs.workato.com/recipes/version-management.html)).

Typed tree views matter. Zapier added nested trees only in May 2026, and its `key__field` naming convention is left over from flatter handling (the second half is my inference) ([Zapier enhanced mapping](https://help.zapier.com/hc/en-us/articles/46001908703757-Enhanced-field-mapping-makes-structured-data-easier-to-work-with)). References by name are fragile: Pipedream requires renamed step references to be updated by hand ([Pipedream overview](https://pipedream.com/docs/workflows/overview)). Files generally travel by reference rather than inline ([Activepieces passing data](https://www.activepieces.com/docs/flows/passing-data), [Zapier constraints](https://docs.zapier.com/platform/build/operating-constraints)). n8n's move to remove in-memory binary mode in 3.0 confirms that lesson ([n8n v3 changes](https://docs.n8n.io/changelog/v30-breaking-changes)). Most products also offer small built-in storage: n8n data tables, Zapier Tables, Make data stores, Workato lookup tables, Pipedream data stores, and Activepieces tables and store.

### Connections keep secrets out of definitions, and differ on who owns them

A connection is a stored, encrypted credential that workflows point to. That one indirection delivers most of the benefit: reconnecting fixes every workflow using it, and exports carry no secrets. Power Automate adds a second indirection, the connection reference, so a solution can move between environments and bind to different credentials on import ([Microsoft connection references](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/create-connection-reference)). A connector's auth definition usually declares its form fields, how to inject the secret into requests, and a test call. n8n's credential files show the pattern ([n8n credential files](https://docs.n8n.io/connect/create-nodes/build-your-node/reference/credentials-files)), and Make requires a "whoami"-style test request ([Make connections tutorial](https://developers.make.com/custom-apps-documentation/create-your-first-app/apps-environment/connection)).

| Platform | Default owner | Documented protection |
|---|---|---|
| n8n | User or project; shares grant "Can use" | Instance key protects rotatable data keys; AES classes for CBC and GCM both exist; default not confirmed |
| Zapier | One user; shareable on Team | AES-256 at rest; key management undocumented |
| Make | Whole team can use and manage | At-rest design barely documented |
| Power Automate | Environment-scoped; consent per connection and flow | Central API Hub credential service; encryption detail not read |
| Workato | Workspace | Per-workspace main key, hourly keys, data keys; AES-256 |
| Pipedream | Workspace | AWS KMS, AES-GCM, loaded into isolated VM |
| Activepieces | Project; admin global connections | `aes-256-cbc` with instance key, no retrieval API |

Sources: [n8n key rotation](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/rotate-encryption-keys), [n8n sharing](https://docs.n8n.io/administer/manage-credentials/share-credentials-securely), [n8n cipher](https://github.com/n8n-io/n8n/blob/master/packages/core/src/encryption/cipher.ts), [Zapier connections](https://help.zapier.com/hc/en-us/articles/36818633398157-App-connections-on-Zapier), [Zapier security](https://zapier.com/security-compliance), [Make connections](https://help.make.com/connect-an-application), [Microsoft data sources](https://learn.microsoft.com/en-us/power-platform/admin/security/connect-data-sources), [Workato keys](https://docs.workato.com/security/data-protection/encryption-key-management/), [Pipedream security](https://pipedream.com/docs/privacy-and-security), [Activepieces security](https://www.activepieces.com/docs/admin-guide/security/practices), [Activepieces encryption](https://github.com/activepieces/activepieces/blob/main/packages/server/api/src/app/helper/encryption.ts).

Three leak paths recur. Someone allowed only to use a credential can send it to a URL they control, which is why n8n has Allowed HTTP Request Domains ([n8n credentials](https://docs.n8n.io/build/understand-workflows/create-and-edit-credentials)). Run history can expose data, so n8n hides data from runs that used a credential the viewer cannot use ([n8n executions](https://docs.n8n.io/build/understand-workflows/understand-executions)). Logs are the third: Make will not show request logs for custom apps at all without sanitization rules ([Make sanitization](https://developers.make.com/custom-apps-documentation/app-components/base/sanitization)). Zapier warns that Webhooks by Zapier credentials sit in plaintext step fields that anyone with Zap access can read ([Zapier API requests](https://help.zapier.com/hc/en-us/articles/44391646192397-Ways-to-make-API-requests-in-Zapier)). Microsoft admits a further gap: connection permission is not tied to a flow version, so a co-owner can change what a granted flow does ([Microsoft drafts](https://learn.microsoft.com/en-us/power-automate/drafts-versioning)).

Ownership is the long-term operational problem. A flow's identity includes its owner in non-solution Power Automate flows, and it falls to the Low profile when the owner leaves, which is why Microsoft built service principals ([Microsoft sharing](https://learn.microsoft.com/en-us/power-automate/create-team-flows), [Microsoft limits](https://learn.microsoft.com/en-us/power-automate/limits-and-config), [Microsoft service principals](https://learn.microsoft.com/en-us/power-automate/service-principal-support)). Workato's workspace owns recipes, so they survive departures ([Workato collaboration](https://docs.workato.com/en/user-accounts-and-teams/team-collaboration.html)). Runtime identity needs an explicit rule as well: n8n's triggered runs act as whoever last published ([n8n personal credentials](https://docs.n8n.io/administer/manage-credentials/use-personal-credentials-in-projects)).

### Integrations are a declared contract plus an HTTP escape hatch

Catalogue counts are marketing and do not compare cleanly. Zapier's site says 10,456+ apps while its developer docs say 9,000+ ([Zapier apps](https://zapier.com/apps), [Zapier MCP](https://docs.zapier.com/mcp/home)). n8n advertises 2,000+ and lists 2,629, yet its core package declares 443 nodes ([n8n integrations](https://n8n.io/integrations/), [n8n package](https://github.com/n8n-io/n8n/blob/master/packages/nodes-base/package.json)). Make claims 3,500+ ([Make integrations](https://www.make.com/en/integrations)). Microsoft says "over 1,000", and my predecessor's count of its list pages found about 1,577 for Power Automate, which is approximate ([Microsoft custom connectors](https://learn.microsoft.com/en-us/connectors/custom-connectors/), [Microsoft list](https://learn.microsoft.com/en-us/connectors/connector-reference/connector-reference-powerautomate-connectors)). Workato claims 1,200+, Pipedream 3,000+, and Activepieces' public API returned 774 pieces ([Workato pricing](https://www.workato.com/pricing), [Pipedream pricing](https://pipedream.com/pricing), [Activepieces catalogue](https://cloud.activepieces.com/api/v1/pieces)).

Underneath, a connector is the same contract everywhere: an auth definition, a set of triggers, a set of actions, field schemas, and rules for pagination and errors. Authoring style is what varies. Zapier's shape is auth, triggers, creates and searches, built in a UI or CLI ([Zapier structure](https://docs.zapier.com/platform/quickstart/zapier-integration-structure)). n8n offers declarative JSON routing for REST and programmatic TypeScript, which is required for all triggers ([n8n building style](https://docs.n8n.io/connect/create-nodes/plan-your-node/choose-a-node-building-style)). Make's apps are JSON plus its IML template language, with shared base settings inherited by modules ([Make base](https://developers.make.com/custom-apps-documentation/create-your-first-app/apps-environment/base)). Microsoft connectors are OpenAPI 2.0 files only, with 3.0 unsupported ([Microsoft OpenAPI](https://learn.microsoft.com/en-us/connectors/custom-connectors/define-openapi-definition)). Workato's is a Ruby-style kit with `poll`, `dedup` and webhook hooks ([Workato SDK triggers](https://docs.workato.com/developing-connectors/sdk/sdk-reference/triggers.html)). Pipedream and Activepieces use JavaScript or TypeScript packages, and Activepieces distributes them via npm and pins each step to an exact version ([Pipedream components](https://pipedream.com/docs/components), [Activepieces piece syncing](https://www.activepieces.com/docs/install/architecture/piece-syncing)).

Connector versioning matters once real workflows depend on connectors. n8n keeps the node version a saved workflow was built with ([n8n versioning](https://docs.n8n.io/connect/create-nodes/build-your-node/reference/versioning)). Activepieces steps never auto-upgrade ([Activepieces piece syncing](https://www.activepieces.com/docs/install/architecture/piece-syncing)). Zapier uses semver, and promotion blocks undeclared breaking changes, though removed output keys go undetected ([Zapier versions](https://docs.zapier.com/integrations/manage/versions)). The trust model matters too: n8n states that community nodes have full access to the host machine, and turns unverified packages off by default in 3.0 ([n8n risks](https://docs.n8n.io/integrations/community-nodes/risks), [n8n v3 changes](https://docs.n8n.io/changelog/v30-breaking-changes)).

The HTTP step is what makes a small catalogue viable. The best forms reuse stored credentials: n8n's predefined credential type, Zapier's API by Zapier, Activepieces' Custom API Call, Pipedream's HTTP Request action, and Make's universal module and HTTP app with built-in pagination ([n8n HTTP Request](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.httprequest), [Zapier API requests](https://help.zapier.com/hc/en-us/articles/44391646192397-Ways-to-make-API-requests-in-Zapier), [Activepieces custom API](https://www.activepieces.com/docs/build-pieces/piece-reference/custom-api-calls), [Pipedream HTTP](https://pipedream.com/docs/workflows/building-workflows/http), [Make HTTP](https://apps.make.com/http)). At Power Automate, HTTP is premium ([Microsoft child flows](https://learn.microsoft.com/en-us/power-automate/create-child-flows)), and tier is a commercial boundary, with roughly 1,416 premium to 181 standard connectors by the same approximate count ([Microsoft premium list](https://learn.microsoft.com/en-us/connectors/connector-reference/connector-reference-premium-connectors), [Microsoft standard list](https://learn.microsoft.com/en-us/connectors/connector-reference/connector-reference-standard-connectors)).

### Testing usually touches real systems, and only three products mock well

Zapier's action tests run live and can change data ([Zapier test steps](https://help.zapier.com/hc/en-us/articles/18811411817741-Test-Zap-steps)). Make's Run once acts on real services with no documented dry-run mode ([Make active and inactive](https://help.make.com/active-and-inactive-scenarios)). Power Automate has no sandbox, and drafts cannot be tested without publishing; Microsoft says it is "exploring" a second runtime representation ([Microsoft drafts](https://learn.microsoft.com/en-us/power-automate/drafts-versioning)).

Three products provide real mocking. n8n pins a node's output so that later manual runs reuse it, and Debug in editor copies a failed run's data back into the canvas, turning a production failure into a repeatable test ([n8n pinning](https://docs.n8n.io/build/work-with-data/pin-and-mock-data), [n8n debug](https://docs.n8n.io/build/understand-workflows/understand-executions/debug-executions)). Power Automate's static results make an action succeed or fail with pasted outputs without running it ([Microsoft test flows](https://learn.microsoft.com/en-us/power-automate/guidance/coding-guidelines/test-cloud-flows)). Workato goes furthest with test cases: a mocked trigger, mocked steps, data checks, and an API for CI ([Workato test automation](https://docs.workato.com/test-automation.html)). Its mocks still evaluate input fields while skipping the external call, per a search excerpt ([Workato test setup](https://docs.workato.com/test-automation/test-case-set-up.html)).

Smaller ideas are worth noting. n8n flags now-stale nodes as "dirty", and Pipedream marks later steps stale when earlier ones change ([n8n dirty nodes](https://docs.n8n.io/build/understand-workflows/understand-executions/understand-dirty-nodes), [Pipedream control flow](https://pipedream.com/docs/workflows/building-workflows/control-flow)). n8n gives webhook triggers separate test and production URLs, with the test URL active for 120 seconds ([n8n webhook development](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/workflow-development)). Inspection is universal, including Zapier's per-step Data In, Data Out and HTTP logs, though those logs last only 7 days ([Zapier run details](https://help.zapier.com/hc/en-us/articles/20512774106125-View-specific-Zap-run-details)). Make exposes raw requests through a Chrome extension ([Make DevTool](https://help.make.com/make-devtool)). A warning applies to test modes that behave differently from production: Activepieces skips retries and runs one loop iteration in step tests, so failure behaviour is only visible in real runs ([Activepieces error handling](https://github.com/activepieces/activepieces/blob/main/packages/server/engine/src/lib/helper/error-handling.ts), [Activepieces loop](https://github.com/activepieces/activepieces/blob/main/packages/server/engine/src/lib/handler/loop-executor.ts)).

### Publishing ranges from no draft at all to Git-promoted releases

The basic question is whether editing can happen without touching production. n8n, Zapier and Activepieces say yes: n8n autosaves drafts and production runs the published version, Zapier allows one draft per Classic Zap, and Activepieces locks a version on publish and copies it to create a new draft ([n8n publish](https://docs.n8n.io/build/understand-workflows/save-and-publish-workflows), [Zapier drafts](https://help.zapier.com/hc/en-us/articles/9693520498445-Create-Zap-drafts-and-versions), [Activepieces versioning](https://www.activepieces.com/docs/flows/versioning)). Power Automate offers draft and publish only for solution flows ([Microsoft drafts](https://learn.microsoft.com/en-us/power-automate/drafts-versioning)). Workato requires stopping a recipe to edit it ([Workato start and stop](https://docs.workato.com/recipes/start-and-stop.html)). Make's documented model has an active toggle and optional saved versions kept 60 days, with no draft and production split in what was read ([Make version control](https://help.make.com/scenario-version-control)). Pipedream separates only through GitHub Sync branches ([Pipedream Git](https://pipedream.com/docs/workflows/git)).

Version retention and tooling vary too. n8n keeps 24 hours for all, 5 days on Cloud Pro, and full history on Enterprise, unless versions are named ([n8n history](https://docs.n8n.io/build/manage-workflows/view-change-history)). Zapier keeps none on Free up to one year on Enterprise, with draft comparison Enterprise-only ([Zapier drafts](https://help.zapier.com/hc/en-us/articles/9693520498445-Create-Zap-drafts-and-versions)). Microsoft keeps published records 12 months and offers no notes or compare ([Microsoft drafts](https://learn.microsoft.com/en-us/power-automate/drafts-versioning)). Rollback is everywhere the same safe idea: restore an old version as a new draft or current version, without rewriting history ([Workato versions](https://docs.workato.com/recipes/version-management.html), [Zapier rollback](https://help.zapier.com/hc/en-us/articles/14094586364941-Restore-your-Zap-to-a-prior-version-with-version-rollback)).

The strictly engineering question is what in-flight runs do during a publish, and only some products answer it. Workato and Zapier Next Gen state pinning, as described in step 10. Make's incomplete executions store the blueprint from the time of error ([Make developer docs](https://developers.make.com/llms-full.txt)). n8n stores the workflow with the run, though the notes found no direct statement on publish behaviour. Microsoft does not state it in the pages read, and its own guidance advises resubmitting on the original version while offering no documented setting for it ([Microsoft test flows](https://learn.microsoft.com/en-us/power-automate/guidance/coding-guidelines/test-cloud-flows)).

Promotion between environments is the top layer. Workato gives DEV, TEST and PROD inside a workspace, with deployment history and rollback ([Workato environments](https://docs.workato.com/features/environments.html)). Microsoft Pipelines moves one immutable artifact through stages, validating connections first ([Microsoft pipelines](https://learn.microsoft.com/en-us/power-platform/alm/pipelines)). n8n's Environments preview uses separate instances and a Git branch, and it never moves credential secrets ([n8n environments](https://docs.n8n.io/administer/environments)). Activepieces' releases bring connections over as placeholders to reconnect ([Activepieces releases](https://www.activepieces.com/docs/admin-guide/guides/project-releases)). Approval gates also exist: Zapier Enterprise publishing restrictions and Activepieces Flow Approvals, where the prior version keeps running during review ([Zapier restrictions](https://help.zapier.com/hc/en-us/articles/21705940108941-Enable-publishing-restrictions-in-your-Enterprise-account), [Activepieces approvals](https://www.activepieces.com/docs/flows/flow-approvals)). n8n's Workflow Reviews exclude settings and credentials ([n8n reviews](https://docs.n8n.io/build/manage-workflows/workflow-reviews)).

### Two open engines show the architecture; the closed ones show only behaviour

n8n and Activepieces publish enough to copy the shape. Both use a web tier that takes events, Redis as the broker, workers that do the running, and Postgres as the record, with object storage for large data. n8n's regular mode puts everything in one process, while queue mode separates main, webhook processors and workers, and defaults to 10 concurrent jobs per worker ([n8n queue mode](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode)). Activepieces recommends one flow per 0.5 vCPU, 1 GB worker, plus one app node per 10 workers ([Activepieces production](https://www.activepieces.com/docs/install/configure-operate/production-setup)). It also keeps database and Redis credentials out of workers, per its production guide, a strong control for running untrusted steps, although its Workers page describes pulling directly from Redis ([Activepieces workers](https://www.activepieces.com/docs/install/architecture/workers)). Its benchmark shows where the bottleneck goes: synchronous throughput rose from 213 requests per second at 40 workers to 777 at 160, Postgres CPU grew fastest, and workers stayed under a fifth of their cap. These are vendor numbers ([Activepieces benchmark](https://www.activepieces.com/docs/install/architecture/benchmark)). n8n similarly warns that low concurrency across many workers can exhaust the database pool ([n8n queue mode](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode)).

Pipedream shows the alternative design. Each deployed version gets its own VM with isolated RAM and disk, and a worker handles one request at a time, shutting down after about five idle minutes ([Pipedream security](https://pipedream.com/docs/privacy-and-security), [Pipedream settings](https://pipedream.com/docs/workflows/building-workflows/settings)). Its control-flow boundaries each compile to a separate function, which is why the timeout resets at each one and long waits are cheap ([Pipedream control flow](https://pipedream.com/docs/workflows/building-workflows/control-flow)). Make describes a database-transaction-like lifecycle of initialization, operation, commit or rollback, and finalization ([Make phases](https://help.make.com/scenario-execution-cycles-and-phases)). Zapier and Workato document behaviour and quotas but not workers, and the notes found no published ordering or exactly-once guarantee from Zapier, Make or Workato.

Concurrency control has three layers. Workato defaults to one job at a time per recipe and sells more ([Workato settings](https://docs.workato.com/recipes/settings.html), [Workato pricing](https://www.workato.com/pricing)), and even so a long action lets the next job start out of order ([Workato long actions](https://docs.workato.com/recipes/long-actions)). Power Automate leaves control off by default, warning that turning it on cannot be undone without deleting and re-adding the trigger, and that waiting runs are capped at 10 plus the parallelism setting ([Microsoft limits](https://learn.microsoft.com/en-us/power-automate/limits-and-config)). Make meters an organisation pool of Processing Units by memory ([Make parallel capacity](https://help.make.com/parallel-capacity)), and Activepieces limits per project, retrying over-limit runs with backoff instead of dropping them ([Activepieces concurrency](https://www.activepieces.com/docs/admin-guide/guides/manage-concurrency)). Overflow policy deserves explicit design: Make's full webhook queue returns 400, while Pipedream's Free queue drops events with an email ([Make webhooks](https://help.make.com/webhooks), [Pipedream concurrency](https://pipedream.com/docs/workflows/building-workflows/settings/concurrency-and-throttling)). Zapier holds a polling burst of 100 or more events for confirmation, a protection called flood protection, and replays at one per second ([Zapier limits](https://help.zapier.com/hc/en-us/articles/8496181445261-Zap-limits)).

A tenant also needs protection from its own workflows. Activepieces' March 2026 postmortem describes a Delay change that made flows restart from the beginning instead of resuming, flooding Redis and degrading queues for all users ([Activepieces postmortem](https://www.activepieces.com/docs/handbook/engineering/postmortems/2026-03-19-redis-and-delay-overload)). Resume logic is therefore the most dangerous code in such a system, and it needs caps on how many jobs a tenant can create (my inference).

### Error handling is four layers, and retry windows differ by 1,000 times

The layers are automatic retry of a step, a designed error path inside the workflow, a workflow-level handler or alert, and after-the-fact replay by a person.

| Platform | Automatic retry | Designed error path | Replay after failure |
|---|---|---|---|
| n8n | 2 to 5 tries, up to 5 seconds apart | Error output branch, error workflow | Resumes at failed node, which reprocesses all its items; current or original workflow |
| Zapier | Autoreplay: 5 tries over about 10 h 35 min | Handler path, which turns off Autoreplay | Errored steps only, or full replay on the current version; within 60 days |
| Make | 8 tries over about 7 h 51 min; Retry handler default 3 at 15 min | Dotted route with Skip, Retry, Resume, Commit or Rollback | Incomplete execution from failed module; run replay re-runs everything |
| Power Automate | Policy-based; default count disputed across pages; custom up to 90 | `runAfter`, try and catch scopes | Resubmit; bulk 20; start point undocumented |
| Workato | Up to 3 at 1 to 10 seconds, off by default | Handle errors block | Rerun whole job on latest version; may duplicate |
| Pipedream | 8 tries over 10 hours, from the failed step | Code `try/catch`, `$errors` stream | Replay on newest version |
| Activepieces | 4 attempts at about 4, 8, 16 seconds (derived from code) | Continue on failure | Retry from failed step using the saved log |

Sources: [n8n workflow-execute](https://github.com/n8n-io/n8n/blob/master/packages/core/src/execution-engine/workflow-execute.ts), [n8n error handling](https://docs.n8n.io/build/flow-logic/handle-errors-gracefully), [n8n view executions](https://docs.n8n.io/build/understand-workflows/understand-executions/view-all-executions), [Zapier replay](https://help.zapier.com/hc/en-us/articles/19220226086797-What-is-replay), [Zapier error handling](https://help.zapier.com/hc/en-us/articles/22495436062605-Set-up-custom-error-handling), [Make automatic retry](https://help.make.com/automatic-retry-of-incomplete-executions), [Make error overview](https://help.make.com/Overview-of-error-handling), [Make run replay](https://help.make.com/scenario-run-replay), [Microsoft limits](https://learn.microsoft.com/en-us/power-automate/limits-and-config), [Microsoft designer](https://learn.microsoft.com/en-us/power-automate/flows-designer), [Microsoft bulk resubmit](https://learn.microsoft.com/en-us/power-automate/how-tos-bulk-resubmit), [Workato error handling](https://docs.workato.com/recipes/best-practices-error-handling.html), [Workato rerun](https://docs.workato.com/recipes/rerun-job.html), [Pipedream settings](https://pipedream.com/docs/workflows/building-workflows/settings), [Pipedream inspect](https://pipedream.com/docs/workflows/building-workflows/inspect), [Activepieces constants](https://github.com/activepieces/activepieces/blob/main/packages/server/engine/src/lib/handler/context/engine-constants.ts), [Activepieces durable execution](https://www.activepieces.com/docs/install/architecture/durable-execution).

A retry window of seconds handles a network blip, while one of hours handles an outage. n8n, Workato and Activepieces offer only the short window, and Activepieces waits inside the worker with an in-process timer, holding capacity ([Activepieces error handling](https://github.com/activepieces/activepieces/blob/main/packages/server/engine/src/lib/helper/error-handling.ts)). The hours-long retriers must persist the retry state rather than hold a process (my inference). Zapier makes a notable trade-off: adding a handler disables Autoreplay for that Zap, so a user cannot have both ([Zapier error handling](https://help.zapier.com/hc/en-us/articles/22495436062605-Set-up-custom-error-handling)). Make's error naming is itself in flux. Current docs say Skip and Retry where older pages say Ignore and Break; the mapping between them is inferred from matching descriptions, and no page states it.

Replay is where duplicate actions originate. n8n warns that its failed node reprocesses every item, including those already handled, and recommends upserts ([n8n view executions](https://docs.n8n.io/build/understand-workflows/understand-executions/view-all-executions)). Make's Rollback only reverts ACID-tagged modules, mostly databases, so third-party side effects stand ([Make phases](https://help.make.com/scenario-execution-cycles-and-phases)). Its "Commit trigger last" setting moves the polling position only after downstream work commits ([Make settings](https://help.make.com/scenario-settings)), which amounts to at-least-once delivery (my inference). No platform in the notes passes a general idempotency key to connectors, although Activepieces' AI metadata lets actions declare themselves idempotent ([Activepieces AI metadata](https://www.activepieces.com/docs/build-pieces/piece-reference/ai-metadata)). That gap is open for FlowBridge.

Automatic disabling stops runaway failures. Zapier pauses a Zap at 95% errors over 7 days ([Zapier advanced settings](https://help.zapier.com/hc/en-us/articles/14167175792909-Decide-how-your-Zap-handles-errors-with-advanced-settings)). Make deactivates after 3 consecutive errors by default, and at the first error for instant scenarios ([Make error overview](https://help.make.com/Overview-of-error-handling), [Make settings](https://help.make.com/scenario-settings)). Power Automate turns flows off after 14 days of continuous errors or throttling ([Microsoft limits](https://learn.microsoft.com/en-us/power-automate/limits-and-config)). n8n offers the same as an opt-in after 3 crashes ([n8n executions variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/executions)), and Workato may stop a recipe after 60 consecutive trigger errors ([Workato start and stop](https://docs.workato.com/recipes/start-and-stop.html)).

### Monitoring starts with the run list, and alerting is mostly a paid afterthought

Every product has a filterable run list with drill-down, and this is the feature operators use all day. Make adds readable run names and a source-run link for replays ([Make history](https://help.make.com/scenario-history)). n8n lets workflows set searchable custom metadata ([n8n custom data](https://docs.n8n.io/build/understand-workflows/understand-executions/customize-executions-data)). Pipedream keeps a `trace_id` constant across retries of one event while `id` changes per execution ([Pipedream triggers](https://pipedream.com/docs/workflows/building-workflows/triggers)). Retention sets the replay horizon: Zapier replay needs to happen within 60 days, Workato deletes action data and disables reruns after expiry at 30 or 90 days by plan, and Power Automate stores runs 30 days ([Zapier replay](https://help.zapier.com/hc/en-us/articles/19220226086797-What-is-replay), [Workato retention](https://docs.workato.com/security/data-protection/data-retention/), [Microsoft limits](https://learn.microsoft.com/en-us/power-automate/limits-and-config)). Activepieces keeps 30 days, with paused runs bounded by it ([Activepieces limits](https://www.activepieces.com/docs/install/reference/limits)).

Native alert rules are rare. n8n leaves alerting to error workflows or external tools, in the pages read. Workato's RecipeOps implements alerts as recipes ([Workato RecipeOps](https://docs.workato.com/en/connectors/recipeops)), which means monitoring depends on the platform being monitored (my inference). Power Automate alert rules require Azure Monitor and Application Insights in a Managed Environment ([Microsoft Application Insights](https://learn.microsoft.com/en-us/power-platform/admin/app-insights-cloud-flow)). Zapier's Alerts is Enterprise ([Zapier Alerts](https://help.zapier.com/hc/en-us/articles/29206590194445-Alerts-is-now-generally-available)). The most copyable low-tier pattern is noise-limited email: Pipedream sends one per error, per workflow, per 24 hours, and Activepieces sends only the first failure per flow per day, with a summary ([Pipedream errors](https://pipedream.com/docs/workflows/building-workflows/errors), [Activepieces projects](https://www.activepieces.com/docs/admin-guide/guides/structure-projects)).

For operators, Activepieces' Health page separates internal errors from flow errors and shows running, queued and stuck jobs ([Activepieces health](https://www.activepieces.com/docs/admin-guide/guides/health)). That distinction answers "is it us or the customer's workflow?". n8n exposes health endpoints, Prometheus metrics and preview OpenTelemetry spans ([n8n monitoring](https://docs.n8n.io/deploy/host-n8n/keep-n8n-running/monitor-n8n), [n8n OpenTelemetry](https://docs.n8n.io/deploy/host-n8n/keep-n8n-running/trace-executions-with-opentelemetry)). Fragmentation is a warning from Microsoft: admin analytics excludes solution flows, the automation center covers only solution flows, and the Dataverse run table is explicitly lossy ([Microsoft admin analytics](https://learn.microsoft.com/en-us/power-platform/admin/analytics-flow), [Microsoft automation center](https://learn.microsoft.com/en-us/power-automate/automation-center-overview), [Microsoft Dataverse runs](https://learn.microsoft.com/en-us/power-automate/dataverse/cloud-flow-run-metadata)).

Sensitive data in history needs a control as well. Workato masks per step, and n8n redacts input and output while keeping status and timing ([Workato masking](https://docs.workato.com/features/data-masking.html), [n8n redaction](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/redact-execution-data)). Make warns that "Keep data confidential" limits error recovery ([Make settings](https://help.make.com/scenario-settings)), because a run that stores no data cannot replay it, a trade-off Workato states too ([Workato settings](https://docs.workato.com/recipes/settings.html)).

### Administration sells isolation and separation of duties

Tenancy models differ more than role names. n8n's Cloud limits are per instance, with projects inside ([n8n Cloud concurrency](https://docs.n8n.io/deploy/use-n8n-cloud/understand-concurrency), [n8n projects](https://docs.n8n.io/administer/manage-users-and-access/set-permissions-and-roles-rbac/organize-work-in-projects)). Make uses organisations and teams, where a resource belongs to one team and cannot move ([Make teams](https://help.make.com/teams)). Zapier is moving Enterprise to organisations and workspaces ([Zapier orgs](https://help.zapier.com/hc/en-us/articles/47031545308557-Roles-and-permissions-in-organizations-and-workspaces)). Power Automate has tenant, then environment ([Microsoft environments](https://learn.microsoft.com/en-us/power-platform/admin/environments-overview)). Workato has workspaces with DEV, TEST and PROD, and Activepieces has platform and project ([Workato environments](https://docs.workato.com/features/environments.html), [Activepieces projects](https://www.activepieces.com/docs/admin-guide/guides/structure-projects)). Activepieces enforces tenant separation by scoping queries to `projectId` and `platformId` in the API ([Activepieces isolation](https://www.activepieces.com/docs/install/guarantees/execution-isolation)).

Roles converge on four jobs: administer, build, operate and view. Activepieces has exactly these as Admin, Editor, Operator and Viewer, where Operator can publish and retry but not edit ([Activepieces users](https://www.activepieces.com/docs/admin-guide/guides/permissions)). Make has a similar Team Operator ([Make teams](https://help.make.com/teams)). Workato has Project operator ([Workato test automation](https://docs.workato.com/test-automation.html)). Microsoft shows why this needs thought: its Operator role sees run metadata but not step inputs and outputs, and gaining those requires co-ownership, which Microsoft admits "reduces separation of duties" ([Microsoft operator role](https://learn.microsoft.com/en-us/power-automate/operator-role)). n8n recommends that owners keep a separate Member account partly because "there is no way to see who created a particular workflow" ([n8n instance roles](https://docs.n8n.io/administer/manage-users-and-access/understand-instance-roles)).

Identity and governance are the main paywall. SSO sits on Business at n8n and Pipedream, Team at Zapier and Activepieces, and Enterprise at Make ([n8n SAML](https://docs.n8n.io/administer/manage-users-and-access/verify-user-identity/use-saml), [Pipedream pricing](https://pipedream.com/pricing), [Zapier pricing](https://zapier.com/pricing), [Activepieces pricing](https://www.activepieces.com/pricing), [Make SSO](https://help.make.com/single-sign-on)). Zapier's security page presents SSO as Enterprise, which conflicts with its pricing table ([Zapier security](https://zapier.com/security-compliance)). App allowlisting is becoming the norm: Microsoft's newer connector policies are default-deny, and Zapier accounts created from 5 October 2026 use allowed apps, per a search excerpt ([Microsoft ACP](https://learn.microsoft.com/en-us/power-platform/admin/advanced-connector-policies), [Zapier app access](https://help.zapier.com/hc/en-us/articles/8496307974541-Manage-access-to-apps-in-Zapier)). Audit is split between activity events, usually Enterprise, and runtime events. Microsoft's Purview logs explicitly exclude individual runs ([Microsoft Purview](https://learn.microsoft.com/en-us/power-platform/admin/activity-logging-auditing/activity-logs-power-automate)).

### Templates are stored definitions with the secrets removed and a setup wizard added

A template is an exported definition without credentials, plus guidance for filling the blanks. Make's public library covers over 7,500 use cases, and its authors mark fields for a guided wizard ([Make templates](https://help.make.com/scenario-templates), [Make template authoring](https://help.make.com/create-and-manage-scenario-templates)). Zapier is moving the same way, replacing shared Zap templates on 15 December 2026 with guided templates, where creators control editable fields, per search excerpts ([Zapier share template](https://help.zapier.com/hc/en-us/articles/8496292155405-Share-a-template-of-your-Zap), [Zapier guided templates](https://help.zapier.com/hc/en-us/articles/43465487495181-Guided-templates)). Workato has a community library and Pipedream a share-a-copy link ([Workato community](https://docs.workato.com/en/community-library), [Pipedream sharing](https://pipedream.com/docs/workflows/building-workflows/sharing)). Once definitions are clean JSON without secrets, templates are cheap (my inference), so they belong late in any build order.

### AI arrives in three forms, and only one is a runtime concern

The first form is **AI as builder**: n8n's Assistant and Workflow Builder, Zapier's Copilot, Make's Maia, Microsoft Copilot, Workato's AIRO, and Activepieces' Chat ([n8n Assistant](https://docs.n8n.io/build/ways-of-building-workflows/n8n-assistant), [Zapier pricing](https://zapier.com/pricing), [Make Maia](https://help.make.com/introduction-to-maia-by-make), [Microsoft Copilot flows](https://learn.microsoft.com/en-us/power-automate/create-cloud-flow-using-copilot), [Workato AIRO](https://docs.workato.com/en/airo), [Activepieces chat](https://www.activepieces.com/docs/ai/chat)). The second is **AI as a step**: a model call or agent with tools inside a workflow, such as n8n's cluster nodes, Zapier's AI step, Make AI Agent, Activepieces agents, and Workato's Agent Studio ([n8n AI](https://docs.n8n.io/build/integrate-ai), [Zapier AI](https://help.zapier.com/hc/en-us/articles/8496342944013-Use-AI-by-Zapier-to-analyze-and-return-data), [Make AI Agent](https://help.make.com/introduction-to-make-ai-agent-new), [Activepieces agents](https://www.activepieces.com/docs/agents/overview), [Workato agentic](https://docs.workato.com/en/agentic/agentic)). The third is **the platform as tools for outside AI**: MCP servers at n8n, Zapier, Make and Activepieces, plus Pipedream's whole strategic pivot to Connect ([n8n MCP](https://docs.n8n.io/connect/connect-to-n8n-mcp-server), [Zapier MCP](https://docs.zapier.com/mcp/home), [Make MCP](https://help.make.com/make-mcp-server), [Activepieces MCP](https://www.activepieces.com/docs/mcp/overview), [Pipedream shutdown](https://pipedream.com/docs/workflows)).

Runtime guardrails are the useful part to study. Zapier caps agent steps at a default of 75 tasks per run and offers per-tool "Require approval before running" ([Zapier migration](https://help.zapier.com/hc/en-us/articles/47402591569805-Migrating-from-Agents-to-AI-by-Zapier), [Zapier AI blog](https://zapier.com/blog/zapier-agents-is-now-ai-by-zapier/)). n8n gates a tool call behind human review on a separate channel from the user ([n8n tool review](https://docs.n8n.io/build/integrate-ai/ai-examples/human-in-the-loop-for-tools)). This area is also the most perishable: n8n's Chat Hub is already scheduled for removal in 4.0, Zapier is folding Agents into its AI step, and Pipedream's String is closing ([n8n v3 changes](https://docs.n8n.io/changelog/v30-breaking-changes), [Zapier migration](https://help.zapier.com/hc/en-us/articles/47402591569805-Migrating-from-Agents-to-AI-by-Zapier), [Pipedream shutdown](https://pipedream.com/docs/workflows)).

**The core**, meaning FlowBridge would not count as this category of product without it, is the eight rows at the top: all three trigger mechanisms, branching, mapping, connections, HTTP, custom connector capability, run inspection and replay. The durable wait is effectively core too, since six of seven have it and it shapes the engine itself. It costs far more to retrofit than to include (my judgement).

**Expected in any serious product, though buildable in sequence**, are loops, draft and publish, designed error paths, sub-workflows and approvals. Make shows that a product can succeed without a draft step, and Workato without drafts while keeping full version history, so these are not absolute. They are absent in a way that users notice.

**Optional, and differentiating at this stage**, are the rows that fewer than half of the products cover well: long automatic retries combined with error paths, mocked testing, native alert rules. These are cheap compared with their perceived value, and they are where the incumbents leave the most room. Everything governance-related (SSO, SCIM, custom roles, audit streaming, environment promotion, customer-managed keys, data residency) is optional for an internship and is what vendors reserve for top plans.

**Optional and safe to skip** are large catalogues, templates, RPA and desktop automation, process mining, embedded white-label products, marketplace review, and AI builders.

## What this means for FlowBridge's design

Nine design decisions follow from the evidence. All are recommendations and my judgement, with the supporting facts cited above.

**Store a graph even if the first UI draws a tree.** Save steps with stable IDs and display labels, and save edges separately, each with the statuses it accepts in the manner of `runAfter`. Merges can then arrive later without a migration, avoiding what Zapier and Make went through. Stable IDs also avoid n8n and Pipedream's rename fragility, and the absence of canvas-derived order avoids n8n's position-dependent branches.

**Use one output per step and explicit loop blocks, rather than implicit per-item execution.** n8n's model is the strongest counter-argument, since it makes simple bulk flows very short. But it produces a documented class of errors, and non-technical users cannot see why a step ran 40 times. Loops should keep path-qualified step IDs in the manner of Activepieces' `loop_1:3/approval`, included in the schema from the first milestone even before loops ship.

**Make every run pinned to an immutable version.** The evidence from Zapier's "diverged" error, Workato's and Next Gen's pinning, and Microsoft's advice to resubmit on the original version all point the same way. Storage cost is one row per publish.

**Write the event to Postgres before answering 200.** This closes Activepieces' documented loss path. Treat the queue as rebuildable from the database: a sweeper can re-enqueue any queued run without a live lease. An ingest idempotency key addresses Zapier's duplicate gap and Activepieces' 30-second window. Postgres-first has a cost, since the Activepieces benchmark shows the database as the first bottleneck, but internship-scale traffic will not reach it.

**Save a row per step rather than a periodic checkpoint.** Activepieces' 15-second overwrite means fast steps can finish and be lost in the window, by my reading, even though its docs say only the single in-flight step re-runs. Step rows make resume, retry from failed step, inspection and billing all queries over the same table. n8n's documented latency cost is the trade-off, and large payloads can move to object storage above a threshold.

**Give waits one abstraction and two clocks.** A single waitpoint row type covers delays, approvals, callbacks and durable retries, with a unique constraint on run plus step. Track active execution time separately from total lifetime. Build in a per-tenant cap on job creation, since Activepieces' postmortem shows the failure mode of resume bugs.

**Retry in two tiers, and pass idempotency keys.** Do a few short in-process retries for blips, then durable scheduled retries over hours, using waitpoints so no worker is held. Run the error path only after retries are exhausted, which is the combination Zapier forces users to choose between. Derive a key from run ID and step ID and hand it to connectors. For an ambiguous timeout on a non-idempotent action, stop and ask a person, because Zapier's own wording admits the outcome is unknown.

**Choose a restricted expression language and defer the code step.** n8n's retrofit of engines and task runners, and Activepieces' unsandboxed default, show that JavaScript evaluation drags in sandboxing work. A small path-and-function language with one picker over it covers most mapping, and fails loudly on bad dates and implicit coercions, unlike Zapier and Make. The opposing view is that developers want JavaScript. That is true, and a sandboxed code step can come later as a single isolated feature.

**Treat connectors as versioned declarations, with credentials behind a reference.** Follow n8n's credential shape (fields, inject, test) and Zapier's operating contract of a fixed step time budget plus a callback for slow work. Pin connector versions per step. Encrypt with an authenticated mode such as AES-256-GCM, store a key ID with each record so rotation is possible, and adopt n8n's re-read-before-refresh. Add a domain allowlist per credential and censored logs from the start. Make workflows and connections organisation-owned by default, and define which identity a triggered run acts as.

On licensing, n8n's Sustainable Use License and Pipedream's source-available licence make them references for behaviour, while Activepieces is MIT outside its enterprise directories ([n8n license](https://github.com/n8n-io/n8n/blob/master/LICENSE.md), [Pipedream license](https://github.com/PipedreamHQ/pipedream/blob/master/LICENSE), [Activepieces license](https://github.com/activepieces/activepieces/blob/main/LICENSE)). Get advice before reusing any code. The most valuable reading before design is short: Activepieces' durable execution and waitpoints pages, n8n's queue mode and durable scheduler pages, Zapier's deduplication page, and Microsoft's Logic Apps error handling page.

## FlowBridge should build the run engine first and the canvas fourth

The order follows dependencies: each milestone is testable without the next, and each proof is a behaviour that many products' early versions lacked. The connector choices are my suggestion, picked to exercise different mechanisms rather than for market reasons. Replace them if the project has specific target apps. If time runs short, cut from the bottom of the table, since milestones 1 to 4 together give a real product and milestone 5 gives the reliability story.

| Order | Build | Why at this point | Proof that it works |
|---|---|---|---|
| 1 | Definition schema, immutable versions, `run` and `step_run` rows, queue, worker with lease, reference resolver, If step, HTTP action, webhook and manual triggers | Everything else writes to or reads from these tables | Kill the worker mid-run; another finishes it without re-executing completed steps, and the history shows every step |
| 2 | Durable ingest with idempotency keys; schedules as database rows; polling with cursor, seen-ID list and priming; publish that subscribes and unsubscribes webhooks | Real triggers define the correctness of everything downstream | Send one webhook twice and get one run; restart during a scheduled time and see it fire within grace; turn on a poller and see no backlog flood |
| 3 | Connection store, OAuth 2.0 with refresh, connector contract, test call, log censoring; real connectors covering API key, OAuth, webhook and polling (for example Slack, Google Sheets, Gmail, Stripe) | "Real integrations" is the project's stated bar | Expire a token mid-run and see transparent refresh; revoke it and see a held, replayable run; find no secret in any log |
| 4 | Visual builder, output-tree picker writing expressions, sample capture, single-step test, pinned output, run inspector | Now the UI has a truthful engine to represent | A person who did not build the system creates a three-step flow, then loads a failed production run back in as a test |
| 5 | Waitpoints, delay, approval step, sequential loop, two-tier retry, error path, retry from failed step | These need durable runs and an inspector to be debuggable | An approval survives a restart; a double click resumes once; a 30-minute 503 outage recovers without help; a duplicate invoice is impossible with a key-supporting API |
| 6 | Draft and publish UI with diff, four roles (Admin, Editor, Operator, Viewer), run list filters, noise-limited failure email, health page, usage counter, per-tenant limits, auto-pause on repeated failure | Makes the product operable by someone other than its builders | An Operator retries a run but cannot edit; a looping flow hits its cap without affecting another tenant |
| Stretch | Rejoining branches in the UI, sub-workflows, sandboxed code step, templates, AI step with tool allowlist and approval, AI builder | Each sits on existing primitives | Each ships as a thin feature with no engine rewrite |

Three decisions deserve challenge. Building the canvas fourth risks a project with nothing to demo for a long time, so a scrappy JSON-editor or minimal form page should accompany milestones 1 to 3. Leaving AI to stretch runs against where every vendor is heading, but an AI step is simply one more connector, while a demo of an agent on an unreliable engine shows little. And leaving loops until milestone 5 will feel odd, yet the step ID format needs to anticipate them from milestone 1. Deliberate non-goals: catalogue size, marketplace, SSO, environments, embedding, and multi-region.

## Conclusion

The research changes where the difficulty lies. A workflow product looks like a canvas with a large connector list, and vendors compete in marketing on those two things, yet the evidence of their own corrections points elsewhere: database-backed schedules at n8n, version pinning and a new durable engine at Zapier, an outage caused by resume logic at Activepieces, and a separate runtime for testing that Microsoft says it is still exploring. Those are the costly fixes, and they are all in the layer an internship project can get right from the beginning, because it has no installed base to migrate. A small product with a trustworthy engine would compare well against these vendors on the one thing their retrofits show customers needed.

Combining ideas from different platforms yields a position none of them holds: Microsoft's edge model for the graph, Activepieces' waitpoints, Pipedream's long retries, n8n's pinned test data, and an idempotency key that none documents. FlowBridge's first milestone therefore has one acceptance test worth pinning to the wall: kill the worker halfway through a real run, and show that the run completes, repeats no finished step, and leaves a complete history. Everything else in the build order depends on that demonstration.
